## 1.0 小问题

### (1) uintptr_t
- uintptr_t 的保证是：它一定足够大能装下指针的数值（在 STM32H7 这种 32-bit MCU 上通常就是 32 位无符号整数）。
```c
#define DCACHE_LINE_SIZE 32U

uintptr_t addr = (uintptr_t)&g_fault_rec;
uintptr_t start = addr & ~(uintptr_t)(DCACHE_LINE_SIZE - 1U);

int32_t size = (int32_t)sizeof(g_fault_rec);
int32_t len  = (int32_t)((addr + (uintptr_t)size) - start);
/* len 向上取整到 32 的倍数 */
len = (len + (int32_t)(DCACHE_LINE_SIZE - 1U)) & ~((int32_t)DCACHE_LINE_SIZE - 1);

SCB_CleanDCache_by_Addr((uint32_t*)start, len);
```
- start 把地址向下对齐到 32B 边界
- len 确保覆盖从 start 到 结构体末尾的整个范围
- len 再向上补齐到 32B 倍数，保证 cache line 全覆盖

- 这里地址可能不是按照32字节的放置的（char==1byte uint16_t）
- 上边就是要保证读取的时候是按照32B的方式存储

### (2) __NO_RETURN 
- 函数属性宏:函数不会返回（一旦调用就不会回到调用点，比如死循环、系统复位、直接退出线程等）。
- 告诉编译器：后面的代码“不可达”
- 通常来自 CMSIS 头文件（你工程里可能是 cmsis_compiler.h / cmsis_gcc.h / cmsis_armclang.h 之类），用来给编译器提供优化/告警信息。

### (3) malloc/new - sct中的 *(HEAD)
- sct文件中写了
```c
*(HEAP)
ARM_LIB_HEAP
```
- 工程没有用到 heap（没 malloc/new）
- 或者被裁剪策略认为 heap section 不需要
### (4) __get_MSP();  __DSB();  __ISB();作用  __DMB() ；__set_PRIMASK(pm);	__DMB(); 
- 这些内联函数/宏：一般放在core_cm7.h（或通过 cmsis_compiler.h 间接包含）
1) `__get_MSP();`:读取当前 CPU 的主堆栈指针（Main Stack Pointer, MSP） 的意思。
2) `__DMB()` 是 ARM 的 Data Memory Barrier，保证它前面的内存写操作在它后面的写操作之前对外“生效/可见”。
3) `PRIMASK`:用来控制全局可屏蔽中断
- __get_PRIMASK:保存当前中断状态
- __set_PRIMASK(pm):恢复进入临界区前的状态
4)	`__DMB()`: Data Memory Barrier（数据内存屏障）
- DMB 保证：在它之前的内存读写，在“观察者眼里”不会被重排到它之后。
- 预防，你写数据到buf中，然后更新rb_w指针，但是看成先看到rb_w，但是buf还未写入
- #include "core_cm7.h"

## 1.1 总体的问题
### (1) .ANY (+RW +ZI)
- 指示链接器，将项目中所有目标文件里的RW数据和ZI数据，都放置到当前定义的这块内存区域（通常是RAM）中
- 如果当前项目空间不足，会尝试将剩余的填充到下一个包含这个的区域
- 嵌入式链接脚本中用于自动、灵活管理RAM数据布局的关键语法。确保了程序运行时，变量能被正确地放置在可读写的内存中。
### (2) 代码编写-复位
- RUN 中输入命令 → 写入 NOINIT 注入请求 → 系统复位 → 启动阶段 app_init 里跑 POST → 注入生效 → 得到“真正的上电 POST 失败路径证据”

### (3) RW_NOINIT内部存储的东西
#### a.fault_log 
- 写入的方法
```c
__attribute__((section("noinit_section")))
volatile xxx g_xxx;
```
- 工程实现：这段SRAM往往是可缓存（DCache）,所以写完要**SCB_CleanDCache_by_Addr + DSB/ISB**，确保数据真落到 SRAM

#### b.inj_nvm
- 工作两点：
  - RUN 时：写注入请求到 NOINIT 并复位
  - BOOT 时：从 NOINIT 读出注入请求并应用（set），然后清掉（oneshot）
### (4) xor轻度校验失败
- 问题描述：在发送故障注入后复位总是不能够校验通过
- 1.SCB_CleanDCache():这把整个系统所有脏cache行强制写回到对应物理地址
- 2.打印被截断：最初的 dump 一行打印 8 个 word，输出被 shell 缓冲截断（... 000000INJCHK... 粘在一起），
  - 以为xor_ck写了，其实根本没看全
  - 无法判断xor_ck是否为0
  - 把dump改成短行
- 3.严格别名（strict-aliasing）导致的“写了但像没写”
  - 用结构体字段：g_inj_blk.xor_ck = ...
  - 又用 uint32_t* 指针去写/算/校验：(uint32_t*)&g_inj_blk
  - 在标准 C 里，用 uint32_t* 去别名访问 struct 对象属于 严格别名违规（UB）
  - 解决：我们把写入逻辑改成完全一致的访问方式（只用字段/或只用 8-word 明确写），并且校验也用字段 XOR，不再用 uint32_t* 去扫 struct。

## 2. RAM操作
### 2.1 最小RAM跑通
#### 2.1.1 scatter编写
##### (0) 内容
- 连接脚本包含两个section：
  - backup_buffer_section：RAM TM的备份buffer
  - ram_test_section:用来做破坏性March C-测试
##### (1) 内容编写
```c
; *************************************************************
; *** Scatter-Loading Description File generated by uVision ***
; *************************************************************

LR_IROM1 0x08000000 0x00100000  {    ; load region size_region
  ER_IROM1 0x08000000 0x00100000  {  ; load address = execution address
   *.o (RESET, +First)
   *(InRoot$$Sections)
   .ANY (+RO)
   .ANY (+XO)
  }

  RW_IRAM1 0x20000000 0x00020000  {  ; RW data
   .ANY (+RW +ZI)
  }
  RW_IRAM2 0x24000000 0x00050000  {
  * (backup_buffer_section)
  * (stl_cpu_tm12_section)
  .ANY (+RW +ZI)
  }
}

```
#### (2) 解释
- backup_buffer_section：
	- STL做RAM测试（March等）时要备份一小段RAM（保存被覆盖前的数据），测试完再恢复，避免破坏运行数据。
	- 把这段buffer放到指定RAM里，方便你控制“测试范围”和“备份区”不重叠
- stl_cpu_tm12_section：
	- STL里某些CPUTestModule（例如TM1/TM2的上下文、临时变量、或需要放在特定RAM的数据）会要求放在一个固定/独立区域，避免被测试覆盖或便于控制定位
