# 0. 原则
## 1. 证据链闭环
建立对工具链的可追溯、可复现、可更新证据链，使审查员能沿着“源码线/构建线/运行线”一路点开证据，最终闭环到：检测→反应时间→安全状态→去能→锁存→日志。
## 2. 代码编写/交付流程，证据分三条
- 源码线：写完代码 -> 静态分析/规则、评审、偏差闭环
- 构建线：编译/链接 -> 工具链可信度(T3) + 构建可复现 + map/段布局检查
- 运行线：烧录运行 -> 动态测试、故障注入、时序/反应时间证据

# 1. 流程
## 1.1  两条线路概述
### (1) 区别
- 路线A：资格化工具链 + Qualification Kit → 按QKit的边界使用工具，补齐项目侧证据与流程
	- 交付物重点：符合性矩阵（Conformance Matrix）/ IQ-OQ / 变更控制与回归记录。
- 路线B：继续用AC6.15  自检可信度证据 - 把QKit该给的东西自己做出来，并增加一条 “暴露工具潜在错更”的冗余校验链。

### (2) 共同点
- 工具清单 + 基线冻结 (版本、pack、scatter、选项、脚本、库)
- T1/T2/T3分类及影响分析
- 构建可复现证据(log/map/hash/版本号) + map/段布局自动检查

## 1.2  花钱点
### 1.2.1 购买FuSa：钱主要花在 “工具可信度证据包（Safety Manual + QKit + 支持）”

### 1.2.2 不购买FuSa：钱花在 “把 QKit 自己做出来 + 再加一条暴露工具错更的冗余校验链 + 更重的构建环境控制”，人力和持续维护成本显著更高。
#### 1. 人力投入
TOR：定义“AC6.15 在哪些用法边界内必须正确”（选项、语言子集、链接布局、库子集）
TVS：设计并实现用例族（优化/volatile/对齐/weak/段布局/启动与向量/库函数关键行为…）
TVR：每次执行输出 PASS/FAIL、日志、结论、版本号
#### 2.工具
- 冗余校验链：没有FuSa背书，需要用工程化门禁让"错更"尽早暴露
- 更严格的受控构建环境与证据归档基础设施

### 1.2.3 都要花钱的点
- MISRA / 静态分析商业工具
- 单元测试工具 / 覆盖率工具
- 受控构建机/CI + 证据归档

## 1.3 购买FuSa与否两条线路工作
### 1.3.1 买 FuSa（资格化工具链 + Qualification Kit）
- 1) 工具清单 + 冻结基线
- 2) T1/T2/T3分类报告
- 3) Conformance Matrix (符合性矩阵 ，此路难点) -
	- 把声明"工具满足什么/承诺怎么用工具/标准或者供应商要求做到什么"，用一张可追溯的举证，逐条映射到"配置约束、验证活动、测试证据、版本冻结与变更控制"。
	- 它的核心价值不是 防止工具使用越界、把“资格化/验证”的证据变成 可追溯闭环。
	- 逐条对照 Safety Manual：项目的编译/链接选项、库、语言子集、限制项，是否在允许范围内
- 4) IQ / OQ(安装确认/运行确认)
	- IQ：装的对、版本对、能构建
	- OQ：用真实工程选项跑一套最小验证（尤其 scatter/map 关键段、优化级别、关键库函数子集）
- 5) 变更控制（TCR）
	- 工具链/Keil/Pack/CubeMX 任意升级，都触发影响分析 + 最小回归 + 记录

### 1.3.2 不买 FuSa（继续 AC6.15，自证）
在项目使用子集（language subset + compiler options + linker layout + MCU特性）内，AC6.15输出可信；并建立“工具错更可能暴露”的冗余检测链。

- (1) 工具清单 + 冻结基线（必须，且更严格）
	- 工具清单+TOR（工具运行/使用需求说明）
	- 自建 Tool Validation Suite （小用例覆盖 volatile/对齐/位运算/弱符号/段布局）
	- 构建可重复性证据：build log / map / fromelf / scatter / 版本号
	- 变更触发规则落地：任何工具/Pack/脚本/选项变更 → 评审+回归
- (2) T1/T2/T3 分类报告
	- T3（必须重点管）
		- ArmClang/armasm/armlink/fromelf（生成最终镜像/代码）
		- CubeMX/自动代码生成脚本（生成进入工程的源代码/配置）
		- 影响链接布局的脚本/工具（scatter 生成器）
	- T2（验证工具，重点是配置与报告留存）
		- MISRA/静态分析工具
		- 覆盖率工具
		- 单元测试框架/测试执行工具
	- T1（相对轻）
		- 纯文档工具、普通文本编辑器、Git（但 Git 对配置管理很关键，仍要纳入过程控制）
- (3) TOR（Tool Operational Requirements，工具运行需求）
	- 要求编译器/链接器在什么条件下必须正确（“用法边界”要写清楚）
- (4) TVS（Tool Validation Suite）
	- 专门验证AC6.15的测试用例工程/脚本/用例集（小程序 + 构建脚本 + 期望结果）
- (5) TVR（Tool Validation Report）
	- 执行TVS的报告：版本、选项、每个用例PASS/FAIL、日志、结论（用什么版本、怎么跑的、结果如何、结论是什么）
- (6) 冗余检测 + 严格冻结 + 升级回归
	- 构建可复现、map 自动校验、warning 策略、运行时签名、回归门禁等

# 2. 重要部分
## 2.1. 建立工具清单 + 冻结基线
### 2.1.1 清单
- 编译器/汇编器/链接器（ArmClang/armasm/armlink 或等价）
- IDE/构建系统（Keil MDK、构建脚本）
- 代码生成器（STM32CubeMX、可能还有配置生成脚本）
- 烧录/调试工具（J-Link、CubeProgrammer）
- 静态分析/规则检查（MISRA、Lint、Axivion 等）
- 单元测试/覆盖率/仿真（若用）
- 版本管理与发布打包工具（Git、打包脚本）
- 外部库（HAL/LL、CMSIS、STL 等——它们更多属于 SOUP/第三方软件，但同样要纳入“受控基线”）
### 2.1.2 分级
#### (1) 重点（高优先级）
- 编译器/汇编器/链接器（ArmClang + armlink / fromelf 等）
- 构建系统（Keil 工程/脚本、命令行构建、后处理脚本）
- 代码生成器（STM32CubeMX：它会生成初始化/中断/时钟等关键代码）
- 会改写/插桩代码的工具（例如自动格式化不算；但自动重构、自动插桩要算）
#### (2) 中优先级（看是否依赖其结果作“安全结论”）
- 静态分析工具（是否用它来证明满足 MISRA、无缺陷等）
- 单元测试框架/覆盖率工具（覆盖率数据是否进入安全证据）
- 模型/脚本生成器（若生成安全相关代码）
#### (3) 低优先级（通常不需要“资格化”，但要纳入配置管理）
- IDE GUI 本身（uVision 作为“界面”影响较小，但它驱动的编译选项/脚本是高风险点）
- 调试器（J-Link/Trace）一般不进入最终产品输出

## 2.2 静态分析部分 - 只能证明“代码层面更不容易写出低级错误”
### 2.2.1 静态分析的工具
- ArmClang warnings
- clang-tidy - 规则/可维护性/部分缺陷
- cppcheck - 缺陷扫描补盲

通过门槛（建议写进 Static Analysis Plan）
- Safety 模块：0 编译告警（或全部 justify 并审批）
- clang-tidy/cppcheck：0 High/Critical 未关闭
- 工具版本/配置文件冻结；变更触发重跑

结论：静态分析这一块，三件套“可以足够”，条件是“门禁+冻结+闭环”齐全。

## 2.2动态验证 + 故障注入（SIL3 最硬的证据）
### 2.2.1.单元测试（模块级）
- Safety Kernel / 诊断调度 / 通信安全层 / 日志模块
### 2.2.2.集成测试（子系统级）
- RS485 driver + frame + safety gate + safety state 联动
### 2.2.3.系统测试（在板）
- E-STOP、安全输出去能、禁止自动恢复、锁存复位
### 2.3.4.故障注入（必须可复现）
- CRC 错/丢帧/超时
- 看门狗不喂
- RAM/Flash 自检失败（可用 STL 或你自己的自检模块）
- 输出 FAULT 触发（硬件拉脚/软件注入都可以）

通过门槛（你可以定成“审核口径”）
- 每条 SW SRS 都有测试用例与结果
- 故障注入覆盖主要故障类别，并能证明：
- 在规定时间内进入安全状态
- 安全输出确实去能
- 锁存且禁止自动恢复
- 黑匣子日志记录完整

## 2.4 安全分析方法与证据产物
### (1) 范围与安全目标（“要做成什么”）
- 定义安全功能：E-STOP、输出去能、禁止自动恢复、锁存复位、通信安全等
- 定义 安全状态（Safe State） 与恢复条件
- 定义关键时间：检测周期、超时、进入安全状态的最大允许时间

目标：每条安全功能都能写成可测试的需求（输入条件、期望行为、时间要求、复位条件）
### (2) 软件安全需求与追溯
- 把安全功能落成可测试的 SW SRS（软件安全需求）：
 例如“RS485 帧 CRC 错误连续 N 次/超时 T ms → 进入 Safe State，记录日志，锁存”
- 建立追溯矩阵：ReqID → DesignID → Module → TestCase → TestResult
通过门槛
- 100% Safety 需求有对应测试用例
- 所有需求“有证据可引用”（测试报告/日志编号）
### (4)  架构与设计（把“为什么这样做能安全”讲圆）
- 分层架构（你之前的 BSP/Services/Safety 很合适）
- 关键模块设计：
	- Safety Kernel（安全状态机、锁存、复位门槛）
	- Diagnostic Manager（POST + 周期诊断调度）
	- Communication Safety Gate（CRC/序号/超时/错误风暴）
	- Output Safety（去能策略、故障检测、互锁）
	- Black-box Logging（进入安全状态时记录）
	
通过门槛
- 每个安全机制都能回答：检测什么？多久检测？如何确认？触发后做什么？如何锁存？如何复位？

## 2.5 关键点1 独立性/评审闭环
### 2.5.1  RACI（责任矩阵）
把“谁做/谁审/谁批/谁归档”写死，否则审核会问“独立性怎么保证”。
### 2.5.2 门禁表（Gate Checklist）
把关键门槛做成 1 页 checklist（审查时就是“过不过”的开关）：
- Gate0：工具与基线冻结完成（ToolList/TOR/选项）
- Gate1：静态分析门槛通过（0 warning / 0 high）
- Gate2：构建可复现 + mapcheck PASS
- Gate3：运行线测试 + 故障注入门槛通过（反应时间/锁存/日志）

## 2.6 关键点2 定量时间约束 (FTTI/反应时间)写入需求
“关键时间”，建议统一成可审计口径：
- 检测周期（Diagnostics period）
- 最大检测时间（FDT）
- 最大进入安全状态时间（Fault reaction time）
- FTTI（容许故障时间）
并在 SW SRS 里给出具体 ms。

## 2.7 关键点3 诊断覆盖与 FMEDA 的接口
- 软件要能回答：每个故障模式“靠什么检测、检测周期、触发动作”。这会直接喂给 FMEDA/DC。
- 没有这块，故障注入做得再好也不容易“对齐系统 SIL3 论证”。

## 2.8 关键点4 第三方/生成代码（SOUP）策略
CubeMX、CMSIS、ST Drivers、STL 等必须写清“版本冻结、使用范围、验证策略、已知问题处理”，否则审查会问“你凭什么相信它”。


## 3. 关键词：
- Qualification Kit（工具资格化套件）：工具供应商为帮助用户满足功能安全标准要求而提供的一套完整证据包
	- 边界说明：变成项目中的规则（TOR） 用配置/脚本/CI把规则强制执行
	- 证据包：审计材料中的引用依据    结合IQ/OQ/回归形成闭环
- TOR：Tool Operational Requirements（工具运行/操作需求）
- TVS：Tool Validation Suite（工具验证套件）
- TVR：Tool Verification Results / Report（工具验证结果/报告）
- IQ（Installation Qualification，安装确认）：证明工具链在受控环境中被正确安装、版本明确、可重复安装/可追溯。
		- 装工具+冻结版本+可复现构建证据
- OQ（Operational Qualification，运行确认）：证明在你项目规定的使用边界（TOR）内，工具链运行行为符合预期、结果可复现。
		- 按 TOR 的用法跑测试 + map/段检查 + 回归证据
- 暴露工具潜在错更
